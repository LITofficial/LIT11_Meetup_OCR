# 신청 마감일 스키마 튜닝 실험

## 이번 변경

- 신청 마감일만 generate, 나머지 7개 필드는 extract.
- 기본 설명은 그대로 유지. 개선 설명을 별도 기본값으로 넣거나 자동 적용하지 않음.
- 신청 마감일은 계속 string 타입. 종료 날짜를 계산하는 후처리나 정답 대체 없음.
- 실행 기록에 필드별 method와 모델 배포 설정을 저장.
- 예전 기록 또는 추출 방식이 다른 기록과 비교하면 설명 변경만의 효과가 아님을 안내.

## 로컬/서버 반영

개발 브랜치에서 git pull 후 앱 재실행. 의존성이나 환경변수 추가는 없음.
팀원이 이미 연결했다면 이 변경 커밋을 반영해 재배포하면 됨.
실제 Azure 분석은 별도로 확인해야 하며 성공이 검증된 시연 예제가 아님.

## 실험 순서

1. 공모전 포스터를 선택.
2. 스키마 튜닝 → 수정 활성화 → 기본 설명으로 초기화.
3. 기본 설명으로 한 번 분석. 이번 버전에서 새로 만든 기록이어야 함.
4. 신청 마감일 설명만 아래 문구로 수정.
5. 같은 포스터를 다시 분석하고 변경 전후에서 직전 기록과 비교.
6. 두 실행의 필드별 추출 방식과 모델 배포 설정이 같음을 확인.

수정할 설명:

> 포스터에서 신청·접수·응모를 받는 마지막 날짜를 찾는다. 신청 마감일이 따로 없으면 공모기간·접수기간·응모기간·모집기간에 표시된 날짜 범위의 마지막 날짜만 반환한다. 예를 들어 접수기간이 2026.11.9 ~ 12.11이면 2026-12-11을 반환한다. 연도가 날짜 범위 전체에 공통으로 표시되어 있으면 그 연도를 사용한다. 범위 전체에 연도가 없으면 임의로 만들지 말고 마지막 월·일만 반환한다. 기간 전체, 시작 날짜, 실제 행사 종료일, 결과 발표일은 반환하지 않는다. 해당 정보가 없으면 빈 값으로 반환한다.

## 판정

- 스크린샷의 접수 기간 기준 기대값은 2026-12-11.
- 기본 설명부터 정답이면 해당 실행은 실패→성공 시연 사례가 아님.
- 수정 후에도 기간 전체 또는 빈 값이면 실패 사례로 기록. 성공한 것처럼 후처리하지 않음.
- 행사 날짜의 잘못된 분류는 별도 필드의 문제. 이번 실험에서는 마감일 설명만 바꿔 조건을 유지.
- 실제 발표 전 같은 입력·설정으로 반복 확인해 결과가 안정적인지 판단.
