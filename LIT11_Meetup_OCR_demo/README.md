**질문 = "글자를 어떻게 읽을까?"가 아니라 "읽은 글자를 어떻게 *일정*으로 만들까?"**

## 📖 개념 설명

> 중·고등학생에게 설명한다는 기준. 용어보다 **"무엇을 입력받아 무엇을 내놓는지"** 중심
> 

### 1. OCR — 이미지 속 글자를 읽는 기술

- 이미지 속 글자 = 컴퓨터에겐 글자가 아니라 **그림**
- 복사·검색·저장 등 정보로 쓰려면 **텍스트로 바꾸는 과정** 필요
- 비유: 사진 속 글씨를 사람 대신 타자로 옮겨 적어주는 일
- 한계: 글자만 뽑음 → **뜻은 모름** (어느 날짜가 행사일인지 구분 X)

### 2. Content Understanding — 읽고, 뜻을 이해해서, 양식에 채우는 기술

- 이미지·문서·음성 등 **비정형 콘텐츠**에서 **구조화된 출력**을 만드는 기술
- OCR과의 차이: 글자를 읽은 뒤 **의미를 이해**하고, 정해둔 양식(**스키마**)에 맞춰 채워줌
- 비유: 포스터를 보고 "제목 / 날짜 / 시간 / 장소" 신청서 빈칸을 대신 채우는 일
- 입력 = 이미지, 문서, 영상 등 (OCR 개념 포함)

### 한눈에 비교

|  | OCR | Content Understanding |
| --- | --- | --- |
| **입력** | 이미지 | 이미지·문서·영상 등 |
| **하는 일** | 글자를 텍스트로 변환 | 의미 이해 + 양식에 채움 |
| **출력** | 텍스트 | 구조화된 데이터 (JSON) |

### 예시: 포스터 한 장이 지나가는 과정

**① 포스터 (원본 이미지)**

> 신청 마감 10/20 · 행사 11/11(수) 18:00 · IT-5 B102
> 

**② OCR 결과** — 글자만 뽑힘

```
신청 마감 10/20 행사 11/11(수) 18:00 IT-5 B102
```

- 한 줄짜리 텍스트 → 마감일과 행사일이 섞여 있음

**③ Content Understanding 결과** — 의미를 이해해서 양식에 채움

```json
{
  "title": "...",
  "event_date": "11/11",
  "event_time": "18:00",
  "location": "IT-5 B102"
}
```

- 마감일 10/20은 제외, **행사일만** 선택
- 연도는 포스터에 없어 빠져 있음 → 한계 파트로 연결

## 🧩 핵심 개념

### 1. 파이프라인 (3단계)

`포스터 사진` → `정보 뽑기` → `캘린더에 넣기`

- **포스터 사진**: 찍거나 업로드
- **정보 뽑기**: 어떻게 뽑지? → 답 = Content Understanding (개념 설명으로 연결)
- **캘린더에 넣기**: 뽑은 정보를 일정 파일(.ics)로 만들어 구글·아웃룩 캘린더로 가져오기

### 2. Azure Vision의 한계 (비교 대상)

- 글자·시각 요소만 인식 → 필드 의미 구분 X (행사일 vs 마감일)
- 스키마 기반 구조화 출력 X → 후처리 직접 구현 필요

### 3. 역할 분담

| 구성요소 | 역할 | 한계 |
| --- | --- | --- |
| **Content Understanding** | 필드 스키마 기반 추출 (제목·날짜·시간·장소·주최·URL) | 연도 생략, 날짜 혼재, 모호한 장소 |
| 스키마 튜닝 | 필드 설명으로 연도 처리·행사일 vs 마감일 구분 등을 지시 | 지시로 해결되지 않는 사례는 잔존 |

### 4. Content Understanding 단독 한계 5가지

- 연도 생략
- 모호한 날짜
- 날짜 혼재 (신청 마감 vs 행사일)
- 기간 / 반복 일정
- 장소 모호

### 5. 연결 구조

> 문제 → 파이프라인 3단계 → "정보를 어떻게 뽑지?" → 개념 설명(OCR → Content Understanding) → Content Understanding 한계 → 스키마 튜닝 → 데모로 검증
> 

각 파트 마지막 멘트 = 다음 파트의 질문으로 연결

## 🛠️ 데모 앱 실행 (구현)

발표 기획에 맞춘 Streamlit 앱이 `app.py`에 구현되어 있습니다. **Content Understanding 단독**으로 OCR, 스키마 기반 행사 정보 추출, 기본/개선 스키마 비교, `.ics` 캘린더 다운로드를 진행합니다. Azure AI Language는 사용하지 않습니다.

### 1. 환경 설치

```bash
python -m venv .venv
source .venv/bin/activate             # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env                  # Windows: copy .env.example .env
```

`.env` 파일에서 아래 내용을 확인하세요.

- `AZURE_CU_ENDPOINT`: Japan East 리소스의 엔드포인트(예시 값 포함)
- `AZURE_CU_KEY`: Azure Portal → 해당 Microsoft Foundry 리소스 → **Keys and Endpoint**에서 받은 키. 이 파일은 Git에 올라가지 않도록 `.gitignore`에 지정되어 있습니다.
- `AZURE_CU_COMPLETION_DEPLOYMENT`: `gpt-4.1-mini` 배포 이름
- `AZURE_CU_EMBEDDING_DEPLOYMENT`: `text-embedding-3-small` 배포 이름

API 키를 사용하고 싶지 않다면 `AZURE_CU_KEY`를 비워 두고, 컴퓨터에 Azure CLI를 설치한 후 `az login`을 실행해도 됩니다. 이 경우 사용자에게 해당 리소스의 적절한 데이터 평면 권한이 필요할 수 있습니다.

### 2. 앱 시작

```bash
streamlit run app.py
```

브라우저에 나타나는 로컬 주소(보통 `http://localhost:8501`)로 접속합니다.

### 3. 데모 절차

1. **저비용 연결 테스트:** 포스터를 업로드하고 `OCR만 확인` 모드로 `포스터 분석 실행`을 클릭합니다. `prebuilt-read`는 모델 배포가 없어도 동작합니다.
2. **분석기 준비(최초 1회):** 왼쪽 `Azure 연결` → `분석기 초기 설정` → `Azure 분석기 준비`를 클릭합니다. 이 작업은 모델 배포를 새로 만들지 않지만, 기존 리소스의 두 모델 매핑을 추가·수정하고 새 맞춤 분석기 두 개를 생성합니다.
3. **스키마 튜닝 비교:** `기본 스키마 vs 개선 스키마` 모드에서 실행하면 동일 포스터로 **OCR / 기본 / 개선** 총 세 번의 API 요청을 보냅니다. 세 번의 호출 각각 사용량 요금이 발생할 수 있습니다.
4. **결과 검토:** 행사 날짜와 신청 마감일이 분리됐는지 비교합니다. 연도가 생략된 경우 앱이 임의로 연도를 채우지 않으므로 사람이 직접 확인해야 합니다.
5. **캘린더 다운로드:** 검토한 날짜·시간으로 `.ics`를 만든 뒤 Google Calendar나 Outlook에 가져옵니다. 사용자의 일정이 자동으로 등록되지는 않습니다.

### 발표용 샘플 포스터

`samples/easy_event.pdf`와 `samples/tricky_event.pdf` 두 파일이 있습니다. 간단한 포스터와 **신청 마감일이 행사일보다 더 강조된 어려운 포스터**입니다. 두 번째 샘플은 행사 연도가 생략되어 있어 스키마 튜닝과 사람 검토의 필요성을 보여줍니다. 이 샘플은 가상의 행사 정보이며, 실제 분석 실패/개선 여부는 API 결과를 보고 판단해야 합니다.

샘플을 다시 만들려면 `pip install reportlab` 후 `python scripts/generate_sample_posters.py`를 실행하면 됩니다.

### 주의 사항

- Azure 구독의 CU 처리·모델 토큰 사용량은 요금으로 청구될 수 있습니다. 라이브 데모 전에 비용/크레딧을 확인하세요.
- **2026-11-02 실측:** `Azure for Students` 구독의 기존 Foundry 리소스에서 `prebuilt-read`와 CU 맞춤 분석기 생성·분석을 검증했습니다. 기본 분석기 `lit_meetup_basic_48b618e98b`, 개선 분석기 `lit_meetup_tuned_090dfbf99d`가 모두 `ready`를 반환했습니다. 개선 분석기에 가상의 행사 정보가 있는 테스트 PDF를 REST로 보내 제목, 행사일, 시간, 장소, 신청 마감일, 링크 및 주최를 구조화해 추출한 결과도 `Succeeded`로 확인했습니다.
- 동봉된 **디자인 샘플 PDF 2종**의 실제 추출 정확도와 기본/개선 스키마 간 차이는 발표 전에 각각 재측정해야 합니다. 개선 스키마가 항상 더 정확하다는 보장은 없습니다.
- `gpt-4.1-mini`와 `text-embedding-3-small`은 `prebuilt-document`의 `supportedModels`에서 확인된 모델입니다. 분석기의 품질과 실제 오류 가능성은 별도입니다.
- API 키나 개인 포스터를 GitHub에 커밋하지 마세요. 발표에는 공개 또는 가상의 행사 정보를 사용하세요.


### 추가 기능 사용법

- 여러 JPG, PNG 또는 PDF를 한 번에 선택하고 분석을 실행하면 각 파일을 순서대로 처리합니다. 비교 모드는 파일당 OCR·기본·개선 분석 3회가 실행됩니다. 파일별 실패는 현황에 표시되며 다른 파일의 분석은 계속됩니다. 선택 상자에서 포스터를 바꾸어 상세 결과를 볼 수 있습니다. 파일당 10MB 제한이 적용됩니다.
- 개선 분석 결과의 필드를 선택하면 Azure가 반환한 근거를 확인할 수 있습니다. 이미지에는 페이지 크기와 위치가 제공된 경우 빨간 테두리를 표시합니다. PDF는 페이지 번호와 좌표를 표시합니다. 근거가 없는 필드는 직접 확인해야 합니다.
- 신청 마감일을 연도까지 확인하면 한국 시간 기준 D-day를 표시합니다. 별도의 마감 알림 .ics를 생성해 캘린더에 가져오면 마감일 오전 9시 일정과 하루 전 표시 알림이 생성됩니다. 실제 알림 동작은 사용하는 캘린더 설정에 따릅니다. 앱을 닫은 뒤 앱 자체가 알림을 발송하지는 않습니다.
- 결과는 현재 Streamlit 세션에만 보관됩니다. 포스터 내용이 동일한 파일은 같은 분석 결과를 공유합니다.
