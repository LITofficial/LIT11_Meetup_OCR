## 🚨 문제 상황

> **"포스터 사진 찍어둔 행사, 캘린더에는 언제 넣나요?"**
> 
- 제목·날짜·시간·장소·신청 URL이 레이아웃마다 제각각
- 직접 옮겨 적기 = 번거로움 + 누락 + 오타
- Azure Vision = 글자·시각 요소를 읽을 뿐, 어느 글자가 *행사일*인지 모름

**질문 = "글자를 어떻게 읽을까?"가 아니라 "읽은 글자를 어떻게 *일정*으로 만들까?"**

## 📖 개념 설명

> 중·고등학생에게 설명한다는 기준. 용어보다 **"무엇을 입력받아 무엇을 내놓는지"** 중심
> 

### 1. OCR — 이미지 속 글자를 읽는 기술

- 이미지 속 글자 = 컴퓨터에겐 글자가 아니라 **그림**
- 복사·검색·저장 등 정보로 쓰려면 **텍스트로 바꾸는 과정** 필요
- 비유: 사진 속 글씨를 사람 대신 타자로 옮겨 적어주는 일
- 한계: 글자만 뽑음 → **뜻은 모름** (어느 날짜가 행사일인지 구분 X)

### 2. Content Understanding — 읽고, 뜻을 이해해서, 양식에 채우는 기술

- 이미지·문서·음성 등 **비정형 콘텐츠**에서 **구조화된 출력**을 만드는 기술
- OCR과의 차이: 글자를 읽은 뒤 **의미를 이해**하고, 정해둔 양식(**스키마**)에 맞춰 채워줌
- 비유: 포스터를 보고 "제목 / 날짜 / 시간 / 장소" 신청서 빈칸을 대신 채우는 일
- 입력 = 이미지, 문서, 영상 등 (OCR 개념 포함)

### 한눈에 비교

|  | OCR | Content Understanding |
| --- | --- | --- |
| **입력** | 이미지 | 이미지·문서·영상 등 |
| **하는 일** | 글자를 텍스트로 변환 | 의미 이해 + 양식에 채움 |
| **출력** | 텍스트 | 구조화된 데이터 (JSON) |

### 예시: 포스터 한 장이 지나가는 과정

**① 포스터 (원본 이미지)**

> 신청 마감 10/20 · 행사 11/11(수) 18:00 · IT-5 B102
> 

**② OCR 결과** — 글자만 뽑힘

```
신청 마감 10/20 행사 11/11(수) 18:00 IT-5 B102
```

- 한 줄짜리 텍스트 → 마감일과 행사일이 섞여 있음

**③ Content Understanding 결과** — 의미를 이해해서 양식에 채움

```json
{
  "title": "...",
  "event_date": "11/11",
  "event_time": "18:00",
  "location": "IT-5 B102"
}
```

- 마감일 10/20은 제외, **행사일만** 선택
- 연도는 포스터에 없어 빠져 있음 → 한계 파트로 연결

## 🧩 핵심 개념

### 1. 파이프라인 (3단계)

`포스터 사진` → `정보 뽑기` → `캘린더에 넣기`

- **포스터 사진**: 찍거나 업로드
- **정보 뽑기**: 어떻게 뽑지? → 답 = Content Understanding (개념 설명으로 연결)
- **캘린더에 넣기**: 뽑은 정보를 일정 파일(.ics)로 만들어 구글·아웃룩 캘린더로 가져오기

### 2. Azure Vision의 한계 (비교 대상)

- 글자·시각 요소만 인식 → 필드 의미 구분 X (행사일 vs 마감일)
- 스키마 기반 구조화 출력 X → 후처리 직접 구현 필요

### 3. 역할 분담

| 구성요소 | 역할 | 한계 |
| --- | --- | --- |
| **Content Understanding** | 필드 스키마 기반 추출 (제목·날짜·시간·장소·주최·URL) | 연도 생략, 날짜 혼재, 모호한 장소 |
| 스키마 튜닝 | 필드 설명으로 연도 처리·행사일 vs 마감일 구분 등을 지시 | 지시로 해결되지 않는 사례는 잔존 |

### 4. Content Understanding 단독 한계 5가지

- 연도 생략
- 모호한 날짜
- 날짜 혼재 (신청 마감 vs 행사일)
- 기간 / 반복 일정
- 장소 모호

### 5. 연결 구조

> 문제 → 파이프라인 3단계 → "정보를 어떻게 뽑지?" → 개념 설명(OCR → Content Understanding) → Content Understanding 한계 → 스키마 튜닝 → 데모로 검증
> 

각 파트 마지막 멘트 = 다음 파트의 질문으로 연결

## 🎬 데모 계획 (12분)

사전 준비한 포스터 2종 + 녹화 영상 백업.

### 데모 진행

| 순서 | 시간 | 내용 | 확인 포인트 |
| --- | --- | --- | --- |
| ① | 4분 | **쉬운 포스터: 업로드 → Content Understanding 추출 → 캘린더 반영** | 기본 파이프라인 동작 |
| ② | 6분 | **어려운 포스터: 튜닝 전 실패 → 스키마 튜닝 → 캘린더 반영** | 연도 누락·날짜 혼재가 보정되는 장면 |
| ③ | 2분 | **비포/애프터 표: 튜닝 전 vs 후, 필드별 정확도** | 수치로 개선 확인 |

### 데모 실패 대비

- 라이브 실패 시 녹화 영상으로 즉시 전환
- 포스터는 쉬운 것 / 어려운 것 각 1장씩 사전 검증
- 네트워크·API 지연 대비 응답 JSON 캡처본 준비

> 어려운 포스터는 튜닝 전 Content Understanding이 실제로 틀리는 사례로 선정. 틀리지 않으면 보완 효과 전달 불가

## 🎤 청중 설득 전략

- 초반: 포스터 사진 → 일정 등록 번거로움 = 누구나 겪는 상황으로 공감
- 중반: 서비스 이름보다 **역할과 흐름** 중심
- 한계 먼저 공개: Content Understanding 한계를 숨기지 않고 데모 전에 예고 → 스키마 튜닝의 근거
- 데모: 성공만 보여주지 않고 **실패 → 튜닝 → 성공** 구성

> **글자를 읽는 데서 끝나지 않고, 일정으로 구조화한다.**
